# Project Context

## Project

MariaDB LSP Server (`lsp-server`): a C++ language server for MariaDB SQL, plus a CLI, part of MariaDB Shell and the MariaDB AI Plugins. Goals: LSP features (diagnostics, completion, hover, symbols, …) in VS Code (the separate `vscode-extension` repo) and an in-memory object model of the schemas in a SQL file (outline JSON now; ALTER generation and EER diagrams later). Must be fast on single statements while typing and on 256 MB dumps. The plan is `docs/plans/core-implementation.md` (phases P0–P7, decisions in §5, a "Status" paragraph under each phase).

## Decisions (from the user, 2026-10-15)

- **Work starts from `main`.** The `architecture-review` branch's docs/design are rejected ("limited knowledge, bad ideas"); only the parser's extraction core was taken from it. No ANTLR anywhere.
- **Build like mariadb-shell:** vcpkg manifest via `-DWITH_VCPKG_TRIPLET`, C++23, gtest `run_unit_tests`, copied cmake modules.
- **Client library from the server checkout as the shell does** (static `libmariadbclient` + mysys/strings/dbug), not vcpkg `libmariadb` (too old; rest-daemon still uses vcpkg, no Rennox update exists).
- **Parser maintained by hand.** Generate once, commit `generated/`, apply upstream diffs by hand, record deviations in `UPSTREAM.md`. The value of the extracted parser vs. sync cost is still doubted by the user; re-extraction deferred.
- **REST SQL merged into libmariadbparser** by hand (`mrs_merge.py` did it once; shell's `mysqlshdk/libs/mrs/parser.yy`, pinned shell commit `4f45397`). No `MDBP_WITH_MRS` switch: bison has no conditional sections and unused rules cost nothing.
- **Live connections by URI** as the MCP plugin does; passwords read directly from the shell's secret store (`mariadb-secret-store-<helper>` next to `mariadb-shell`, JSON `{SecretType, SecretID}`; keys `GUI:CONN:<uri>`, `MCP:CONN:<uri>`, or `password`/`user@host[:port]`). Plan §2.11.
- **Where the extension finds the binary:** `mariadb.lsp.path`, else the PATH, else `~/.local/bin`; a download like the shell's comes later. This replaces the plan's "next to `mariadb-shell`" (plan §5 item 4).
- **CLI:** `mariadb-lsp check FILE` (errors or success, exit 1 if any) and `mariadb-lsp outline FILE` (schema JSON); `split`, `tokens`, `tree` for inspection.

## Current State

- **P0–P5 done on macOS** (details in the plan's status paragraphs, numbers in `docs/language-server.md` "Measured", P5 mechanics in its "Completion" and "Live connections" sections). The server has reader/writer/event-loop/request-pool/parser-pool threads, incremental sync with per-statement verdicts that survive edits, diagnostics, document symbols, folding, selection ranges, semantic tokens, completion, hover, definition, highlight, references and rename (document scope), signature help, workspace symbols, `catalogFiles` workspace catalog, live catalogs per connection URI, `mariadb/documentContext|viewport|outline|parseProgress|refreshCatalog`, work-done progress. libmariadbparser is API 2.4 (`mdbp_keyword_count/at`).
- **Live catalog behaviour:** one thread per connection; connects, reads `information_schema`, disconnects (no kept session); server `sql_mode`/version apply unless `documentContext` sets them; refresh interval off by default (`catalogRefreshSeconds`; a change through `didChangeConfiguration` reaches the catalogs already read, `Live_catalog::set_refresh_interval`, counted from the last successful read), but `shellBinary`/`shellBinDir`/`credentialStoreHelper` changes do not reach them (a "not configured" failure is permanent until restart); errors via `window/showMessage` once; invalid URIs are refused, never logged as given. Secret store helpers run one at a time (`run_program` is serialized, pipes close-on-exec, 60 s timeout).
- **Pin single source:** `cmake/mariadb_pin.cmake` reads the `| MariaDB server` row of `libs/mariadbparser/UPSTREAM.md`; bootstrap re-runs when it moves.
- **Shared helpers to use rather than re-implement:** `src/text_util.h` (`iequals`, `lower`, `upper`, `starts_with_word`, `istarts_with`, `icontains`, `collapse`, `trim`, `unquote_identifier`, `join`, `percent_decode/encode`), `keywords.h` (`is_name_symbol`, `is_left_paren`, `quote_identifier`, `backtick_quote`, `builtin_markdown`), `Column::attributes`, `Routine::parameter_list`, `table_for_qualifier` (sql_names.h), public `mdbls/lsp/json_position.h` (`write_position`, `write_range`; makes `rapidjson` a PUBLIC link dependency of the library), `Unchecked_notes` in `syntax_check.h` (the "statement not checked" messages for server and CLI), `Parser_pool::run_all` (submit N jobs and wait for just those; never call from a pool job), `Parser_cache::get` (allocation-free lookup), `k_default_version_id` in `sql_mode.h`, `Statement_index::build_parallel(threads = 0)` = one per core.
- **Known duplication left on purpose (behaviour differs, so merging changes results):** five comment/first-keyword scanners (`statement_index.cc classify`, `sql_mode.cc tokenize`, `catalog.cc may_change_catalog`, `semantic_tokens.cc gap_comments`, `charset.cc next_word`, plus `features.cc starts_with_word` in folding) with different `/*!NNNNN` and `--` rules; string unquoting (`catalog.cc unquote_string` decodes `\n`, `sql_mode.cc read_quoted` does not); token-class name lists in `semantic_tokens.cc` and `syntax_check.cc` (`HEX_STRING` is a string in one, a number in the other).
- **Open from P0–P4:** CI has never run (needs the shell's GCP secrets in this repo); Linux and Windows untested (Windows ported, job written); shell git hooks not adopted (copyright check would block imported sources); `run_unit_tests.py`; cpack (P7); the bounded give-up region of plan §2.6 (an edit that opens a string/comment re-splits to the end of the file; 5–24 ms measured on a dump); semantic tokens do not classify identifiers (the catalog view now exists to do it); a JSON Schema for the outline format; reading objects out of statements with a syntax error.
- **Open from P5:** the secret store's Windows process code has never run; references and rename are document-scope only; `schema_in_use` scans back over all statements per request (cache `USE` positions in the index); catalog name lookups are linear (`find_named`); the workspace reader falls back to latin1 for non-UTF-8 files while the CLI refuses unless told (charset policy not shared); saving one catalog file rebuilds the whole workspace catalog.
- **MCP mode (`lsp --mcp`):** the server connects to nothing; a `Live_catalog` with `fetch`/`fetch_details` asks the client through `mariadb/dbCall` requests (`client_request` + `on_response` in `server.cc`, 120 s per call, `close_pending` releases waiters at shutdown). A reading lists names (tables/views/routines of user schemas are `stub`); `Catalog_view` records stubs it returns (`stubs_met`), and completion/hover/signature help call `with_details` (`language_features.cc`): `Live_catalog::details` queues them for the catalog's own thread, waits ≤ 3 s, and the request runs again on the new snapshot (`apply_details`). Incoming FKs (`1:n`, `1:1` references) are kept on the pointing stub tables. Failed details are not retried until the next reading. The VS Code extension always runs this mode; direct mode stays the default and stays eager.
- **Completion that writes FROM** (`completion.cc`, column case; `Statement_names::query_at` gives the select list and FROM ranges): `SELECT |` → current schema's tables or schemas (dotted items with `retrigger` = `editor.action.triggerSuggest`) → columns; a column of a table not in scope rewrites the qualifiers to an alias and adds FROM / `LEFT OUTER JOIN … ON` first FK either way / n:m through a link table / `CROSS JOIN`. Only when the whole statement parses. An insert touching the item's end goes into the item as a snippet (`name$0 FROM …`) because VS Code applies a same-position additional edit first. Columns are shown `t.col` once a table in scope has an alias.
- **P6 started in `vscode-extension`** (its `.claude/context/language-server.md` covers the client): lookup, lazy start, `documentContext` per document, `refreshCatalog` after DDL runs from an editor, settings sent via `didChangeConfiguration`, `parseProgress` status bar entry (client declines `window.workDoneProgress`), server semantic tokens switched off in the client middleware (they would hide the extension's ANSI_QUOTES marks). Status paragraph under P6 in the plan.
- **Plan decisions still unanswered by the user** (plan §5): REST as keyword after USE/GRANT/REVOKE, offline tree from derivation, incremental sync, C++23+RapidJSON, also reading shell `password` credentials (built: GUI → MCP → shell `password`), SSH tunnels deferred (built: refused).

## Next steps

1. **Layout-aware FROM/JOIN inserts in completion (next).** The completion that adds a table (see "Completion that writes FROM" above) writes everything onto the line being typed: `SELECT s.name, c.title FROM school.student AS s LEFT OUTER JOIN school.enrollment AS e ON e.student_id = s.id LEFT OUTER JOIN school.course AS c ON e.course_id = c.id;` comes out as one 167-character line. Make the inserted parts follow the statement's layout and a width limit. It only places the text it inserts; it never moves existing text (that is formatting, step 2).
   - **Where:** `table_edits` lambda in `libs/mariadblanguageserver/src/completion.cc` (column case of `complete()`), which builds `Text_edit`s: ` FROM <q> AS <a>` at `to_doc(query.select_list.end)` when there is no FROM; otherwise at `to_doc(query.from_tables.end)` one of ` LEFT OUTER JOIN <q> AS <a> ON <cond>` (direct FK), the n:m pair (`link` string: two LEFT OUTER JOINs) or ` CROSS JOIN <q> AS <a>`. The texts start with a space. `to_doc` maps offsets of the sentinel parse back to the document; `begin`/`body_end` are the statement's bounds and `text` the whole document, so the line of any offset is found by scanning `text` back to `'\n'`. `add_columns_with` turns an edit that inserts exactly at `out.replace_end` into the item's own snippet (`insert$0` + `snippet_escape(edit)`) when `options.snippets`.
   - **Rule:** break when the statement already spans lines (a `'\n'` between `begin` and `body_end`), or when the line the insert lands on would be longer than the limit after the insert (count characters, not bytes; the column's own insert text counts too when the FROM goes after it). A break puts each clause on its own line: `\nFROM …`, `\nLEFT OUTER JOIN … ON …` (each JOIN of the n:m pair on its own line), `\nCROSS JOIN …`. `ON <cond>` stays on its JOIN's line; if that line is still over the limit, `ON` goes on the next line one indent level deeper (2 spaces, or the statement's indent unit if it uses tabs). Without a break, keep today's single-space form, so short statements are unchanged.
   - **Indentation:** a new FROM line takes the indentation of the line the statement starts on (whitespace from that line's start up to the statement's first character). A new JOIN line takes the indentation of the line holding the FROM keyword (the line of `query.from_tables.begin`); if the FROM clause already has JOINs on lines of their own, use the indentation of the last one (the line of `query.from_tables.end`).
   - **Line endings:** use `\r\n` when the statement's lines end that way, else `\n`.
   - **Keyword case:** the inserted `FROM`, `LEFT OUTER JOIN`, `CROSS JOIN`, `AS`, `ON` and `AND` are upper case today; make them follow `Completion_options::upper_case_keywords` (`keywordCase`).
   - **Text after the insert point** on the same line (`;`, or ` WHERE …` after the FROM tables) stays where it is, so it ends up after the last inserted line. That is acceptable for this step.
   - **Width setting:** new initialization option `lineWidth` (default 80; 0 = no limit), read in `apply_settings` in `libs/mariadblanguageserver/src/lsp/server.cc` next to `keywordCase` (also via `didChangeConfiguration`), added to `Completion_options` (`include/mdbls/completion.h`) and passed where `server.cc` fills `Completion_options o` (`o.upper_case_keywords`, `o.snippets`). Document it in the initialization options table of `docs/language-server.md`. In vscode-extension: `mariadb.lsp.lineWidth` in `package.json` (integer, minimum 0, default 80), `lineWidth` in `serverSettings` and `LIVE_SERVER_SETTINGS` in `src/lsp/settings.ts`, plus `src/test/lsp/settings.test.ts`.
   - **VS Code snippet trap:** VS Code re-indents every line after the first of a snippet by the current line's indentation, unless the item says `insertTextMode: 1` (asIs, LSP 3.16). When an item's insert text contains a line break (the touching-FROM snippet), write `"insertTextMode": 1` in `completion()` in `src/lsp/language_features.cc` (add a field to `Completion_item`), since the server already computed the indentation. `additionalTextEdits` are applied as they are.
   - **Tests in lsp-server:** `unittest/mariadblanguageserver/completion_t.cc`. `pick()` applies an item's edits and returns the statement; `complete_at(sql, with_schema, max_items, snippets)` sets the options, and needs a parameter for the width (and keyword case). Expected statements over 80 characters change under this rule: `a_second_table_is_joined_on_its_foreign_key` (103), `the_foreign_key_may_point_the_other_way` (99), `n_m_tables_are_joined_through_the_table_linking_them` (167 and 114). `a_table_with_no_foreign_key_is_cross_joined` (75) stays one line. Add cases for:
     - an already multi-line statement (FROM on its own line, indented)
     - a statement inside an indented block, such as a routine body
     - `lineWidth` 0
     - `\r\n`
     - lower-case keywords
     - the snippet with a line break
   - **Other tests:** in `tests/e2e/test_language.py`, `Completion.test_a_column_brings_its_table_and_a_table_asks_again` expects `" LEFT OUTER JOIN orders AS o ON o.customer_id = c.id"` on a line over 80 characters, so it changes. In vscode-extension, `ui-test/tests/08-lsp.test.ts` ("goes from a schema to a table to a column…") compares line 2 with `lineBecomes(editor, 2, …)`. The joined statement is over 80 characters, so it will span lines 2–3: compare `editor.getText()` lines instead. Run `npm run ui-test:lsp`, which deploys and deletes its own sandbox.
   - **Docs:** the "From a schema to a column" part of `docs/language-server.md` (Completion section), the P6 status paragraph in the plan, and the "Completion that writes FROM" entry above.
2. **SQL formatting as its own phase** (`textDocument/formatting`, `textDocument/rangeFormatting`, maybe `onTypeFormatting`). Plan §6 lists formatting as out of scope; add it as a phase first. Before writing code, ask the user for the style:

   - one select item per line, or wrap at the width;

   - subquery indentation;
   - keyword case (reuse `keywordCase`);
   - the width (reuse `lineWidth` from step 1);
   - what to do with statements that do not parse (leave them untouched).

   Build it on the parse tree (`Syntax_tree`/`Statement_names`; clause nodes such as `query_specification`, `select_item_list`, `from_clause`, `table_reference_list`, `opt_where_clause`, `join_table_list` in the grammar `libs/mariadbparser/generated/yy_stub.yy`) and the token list, so comments and whitespace between tokens are known. ## Gotchas / things not to repeat

- **Every rule in `yy_stub.yy` needs exactly one `{ MDBP_R(n); }` action**, or its reductions vanish from the derivation (rule number is `yyn - 1`). `mrs_merge.py` anchors on these numbers as literal text, so regenerating the stub breaks its anchors; it is a one-shot tool.
- **`MDBP_LEX_DEFAULT_VERSION_ID` (`src/mdbp_lex.h`, 130100) and `mdbls::k_default_version_id` (`include/mdbls/sql_mode.h`) must follow the pin's VERSION by hand, together** (next step 2 ties them).
- **Don't point `MARIADB_BOOTSTRAP_DIR` at `../mariadb-server`**: the shell's build uses that checkout at `main`; ours is `../mariadb-server-lsp` at the pin.
- **The pinned server tree for re-extraction** is fetched with `git fetch --depth 1 origin <sha>`; a shallow clone of an older commit does not have it.
- **Worktree agents start from `main`**, not the working branch; they had to reset onto it. A build inside `.claude/worktrees/` cloned vcpkg into `.claude/worktrees/vcpkg` (bootstrap default `../vcpkg`); pass `VCPKG_ROOT` or build outside the worktree.
- **VS Code CMake Tools:** `cmake.sourceDirectory` must be the repo root (not `libs/mariadbparser`, which cannot configure alone) and `cmake.configureSettings` must carry `WITH_VCPKG_TRIPLET`, or `find_package(RapidJSON)` fails. CMake reads the vcpkg toolchain only on a fresh configure, and switching the compiler kit wipes the cache, so after a kit change use "Delete Cache and Reconfigure".
- **The bison output needs `-Wno-unused-but-set-variable`** (clang `yynerrs`); the extracted lexer is compiled without `-Werror`, our own code with the shell's warning set via `mdbls_target_warnings()`.
- **Lex fixtures with invalid UTF-8 must expect `MDBP_UNSUPPORTED`** (library contract), not the server lexer's tokens.
- **`Parser_cache::get` resets the parser when `mdbp_parser_set_version_id` fails**; any hand-rolled cache that ignores that return value drifts from `check`/`tree`/`outline`.
- **`Catalog` lookups that can `push_back` into `m_schemas` (`c_.schema(...)`) invalidate `Schema&` references** held across them (`CREATE TABLE … LIKE` once read freed memory this way).
- **Expected set after a complete statement:** `mdbp_parse_sql` gives none when the prefix is accepted, and appending an unterminated quote makes the lexer emit a token the grammar lacks (MDBP_UNSUPPORTED, no expected set). Re-feed the parse's own tokens to `mdbp_parse_tokens` with `ABORT_SYM` appended instead.
- **Non-reserved keyword probing costs ~100 µs per keyword** (LAC computes the full expected set on each rejection): probe only keywords matching the typed prefix, cache per prefix (`keyword_verdicts`), skip with an empty prefix and mark the list incomplete.
- **Keyword terminal names differ from spellings** (`PARSE_VCOL_EXPR` → `PARSE_VCOL_EXPR_SYM`): look terminals up by `mdbp_keyword_at`, not by guessing names.
- **Request-pool jobs must not submit to the request pool** (null/destroyed at shutdown): post to the inbox and let the loop thread submit.
- **`SELECT ... INTO var` is not a table**: `INTO` names a table only after INSERT/REPLACE (`Token_view::into_table`).
- **Live tests:** the plaintext helper honours `MARIADB_SHELL_USER_CONFIG_HOME` (file `.mariadb-secret-store-plaintext.json` there), so tests use a private store; the sandbox's socket path must stay under 104 bytes on macOS, hence a short temp dir; root needs `--auth-root-authentication-method=normal`.
- **Importing TestCase classes into another e2e module runs them twice** in discovery; import only constants and the test-less `Lsp_test` base.
- **No `Co-Authored-By` lines in commits** (user rule, `~/.claude/CLAUDE.md`); four early commits had them and were rewritten.
